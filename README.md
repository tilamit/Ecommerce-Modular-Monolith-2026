# ShopHub

A .NET 10 **modular monolith** e-commerce application with a React 19 single-page frontend.
One process, one deployable, one SQL Server database - split into four modules whose
boundaries are enforced by the compiler and by tests rather than by convention.

A solution with folders named "Modules" that freely reference each other is a layered
monolith with extra steps. In ShopHub a module can only be reached through its `Contracts`
project, every `DbContext` is `internal` to its own module and owns its own database schema
and 52 architecture tests fail the build the moment any of that stops being true. The
frontend applies the same rule to its feature folders.

```
   Identity            Catalog             Ordering            Auditing
   schema: identity    schema: catalog     schema: ordering    schema: audit
       |                   |                   |                   |
       +------ reachable only through Contracts projects and events ------+
                                   |
                          ShopHub.Api (the host)
                                   |
                        React SPA (Frontend/)
```

## What the application does

**Storefront.** Anonymous product browsing with category, price and stock filters. Every
filter lives in the URL query string, so a filtered view survives a refresh, a share and the
back button. Search has a debounced typeahead that cancels superseded requests.

**Cart and checkout.** A guest cart is kept in `localStorage` and holds only product ids and
quantities, never prices. Every cart render and every checkout re-prices on the server. When
a guest signs in, the local cart is merged into their server cart through an idempotent
request. Guest checkout is supported. A guest order is never attached to an account after the
fact: if that email later registers, a `UserRegistered` event links the guest profile to the
new user without rewriting historical orders.

**Customer account.** Personal dashboard, purchase history with date filters, order detail
and cancellation while an order is still `Pending` or `Confirmed`.

**Administration.** A dashboard that spans all four modules, user management,
product and category CRUD with image upload, offers, order management, the audit trail and
access management, where an admin grants permissions and menu items to a role.

**Audit trail.** Every entity change in every module is captured by a `SaveChanges`
interceptor, queued onto a bounded channel and bulk-inserted by a background service, so
auditing never sits on the request path. The table is append-only: no update endpoint, no
delete endpoint and no admin override.

**API reference.** Generated by the first-party `Microsoft.AspNetCore.OpenApi` package with
Scalar as the UI, at `https://localhost:7003/scalar/v1` in Development.

## How the features work

### Sign-in and sessions

1. `POST /api/v1/auth/login` checks the password and returns a **15 minute access token** in
   the response body. A **7 day refresh token** is set as an `HttpOnly` cookie that JavaScript
   cannot read.
2. The SPA keeps the access token in memory only, then calls `GET /api/v1/auth/me` to load
   the user's profile, permissions and sidebar menu.
3. Shortly before the access token expires, the SPA calls `POST /api/v1/auth/refresh`. The
   server rotates the refresh token: the old one is revoked and a new one is issued. If an
   already-rotated token is ever presented again, the whole token family is revoked and every
   session that came from that sign-in ends.
4. On a page reload the in-memory token is gone, so the SPA silently calls `/refresh` once
   with the cookie to restore the session.

Protection built into sign-in:

| Rule | Behaviour |
|---|---|
| Wrong password or unknown email | Same response and the same time taken, so an attacker cannot tell which emails exist |
| 5 failed attempts | The account is locked for 15 minutes |
| Rate limit | Login, register and refresh allow 5 requests per minute per IP address |
| Device cap | At most 5 active sessions per user; signing in on a sixth device revokes the oldest |
| Absolute limit | A session cannot be kept alive by refreshing for more than 30 days |
| Signing out | Revokes the refresh token on the server and clears the session in the browser |

### Roles, permissions and menus

Access is built from three pieces of data, all stored in the `identity` schema:

| Piece | Decides | Checked by |
|---|---|---|
| **Role** | Which permissions and menus a group of users gets | - |
| **Permission** | What the user is **allowed to do** | Every API endpoint and the SPA route guards |
| **Menu item** | What the user **sees in the sidebar** | The sidebar only |

A user holds one or more roles and their effective permissions are the union of those roles'
permissions. Endpoints never check a role name - they check a permission such as
`catalog.products.write` - so adding a role is a data change through the roles API rather
than a code change or a deploy.

The two seeded roles:

| Role | Permissions | Menus |
|---|---|---|
| **Admin** | All 19 permissions | All 11 menu items |
| **Customer** | `catalog.products.read`, `catalog.categories.read`, `catalog.offers.read`, `orders.read.own`, `cart.own`, `checkout.own`, `dashboard.own` | My Dashboard, Purchase History, My Profile |

All 19 permissions:

| Group | Permissions |
|---|---|
| Catalog | `catalog.products.read`, `catalog.products.write`, `catalog.categories.read`, `catalog.categories.write`, `catalog.offers.read`, `catalog.offers.write` |
| Identity | `identity.users.read`, `identity.users.manage`, `identity.roles.read`, `identity.roles.manage`, `identity.access.manage` |
| Ordering | `orders.read.all`, `orders.read.own`, `orders.manage`, `cart.own`, `checkout.own` |
| Auditing | `audit.read` |
| Dashboards | `dashboard.admin`, `dashboard.own` |

**Menus and permissions are deliberately independent.** A menu item is a link and nothing
more. Showing a link never grants access and hiding a link never removes it. Access is decided
by permissions alone, at three layers:

1. **The sidebar** shows exactly the menu items granted to the user's roles.
2. **Route guards in the SPA** keep a user out of a whole area they cannot use. The
   administration area (`/admin/*`) requires `dashboard.admin` or `identity.users.read`;
   anyone else is sent to a "You do not have access to that page" screen. Inside a page,
   buttons such as **New product** only appear with the matching write permission.
3. **The API** checks the permission on every request and answers `403` when it is missing.
   This is the real security boundary. The first two layers only save the user from clicking
   into something that would fail anyway.

### Access management

**Administration > Access Management** (`/admin/access`) edits both grants for a role side by
side: permissions on the left, menu visibility on the right. Choose a role, tick or untick
boxes and press **Save changes**.

- The API applies the change **immediately**. The server-side permission and menu caches
  are cleared on save, so the very next request from an affected user is checked against the
  new permissions.
- The affected user's **browser** picks up the new sidebar and the new permission list the
  next time they sign in or reload the page.
- Using the screen needs `identity.roles.read` to list roles and permissions and
  `identity.access.manage` to load the menu tree and to save.

**Example: a menu granted without its permissions.** Suppose an admin ticks the
**Access Management** menu for the **Customer** role but leaves **Admin dashboard**
(`dashboard.admin`) and the other admin permissions unticked. This should never be done on
purpose, but it shows how the layers behave:

1. After signing in again, a customer sees an **Access Management** link in their sidebar
   under an "Administration" heading, next to their usual "Your account" links, because the
   menu item was granted.
2. Clicking it opens `/admin/access`. The route guard finds neither `dashboard.admin` nor
   `identity.users.read` in the customer's permissions and redirects to the
   "You do not have access to that page" screen.
3. Calling the API directly does not help either: `GET /api/v1/menus` and
   `PUT /api/v1/roles/{id}/permissions` answer `403` because the customer lacks
   `identity.access.manage`.

The customer can see the link but cannot use any part of the screen or change any
permission. Other combinations behave the same way:

| Menu ticked | Permissions ticked | Result |
|---|---|---|
| Access Management | none of the admin permissions | Link visible, page redirects to the access-denied screen, API answers `403` |
| Access Management | `dashboard.admin` only | The admin area opens, but the page cannot load roles, permissions or menus (`403`) and shows an error with **Try again**; saving is refused |
| Access Management | `dashboard.admin`, `identity.roles.read`, `identity.access.manage` | The page works fully |
| not ticked | `dashboard.admin`, `identity.roles.read`, `identity.access.manage` | No sidebar link, but typing `/admin/access` in the address bar opens a fully working page |

The last row is the reason permissions and menus are separate: hiding a menu is presentation.
To take access away, untick the **permission**.

### User and role management

**Administration > Users** (`/admin/users`, needs `identity.users.read`) lists users with
search, sorting and paging and has an **Activate / Deactivate** button per row, which needs
`identity.users.manage`. The rest of user administration is available through the API with
the same permission: `POST /api/v1/users` to create, `PUT /api/v1/users/{id}` to edit,
`PUT /api/v1/users/{id}/roles` to assign roles and `DELETE /api/v1/users/{id}` to delete.

- **Deactivating** a user revokes all their refresh tokens and clears their cached
  permissions. They cannot sign in or refresh again and their current access token stops
  working when it expires, within 15 minutes at most.
- **Deleting** is a soft delete: the row is flagged rather than removed, so orders and the
  audit trail keep a valid reference.
- Changing a user's roles takes effect on the API immediately.
- Any signed-in user can view and update their own profile under **Your account > My Profile**.

**Roles** are managed through `/api/v1/roles` (`identity.roles.read` to list,
`identity.roles.manage` to create, rename and delete). Role names are unique, the seeded
system roles cannot be deleted and a role that is still assigned to users is refused with
`409` until those users are moved to another role.

### Admin dashboard

**Administration > Dashboard** (`/admin/dashboard`, needs `dashboard.admin`) is one API call,
`GET /api/v1/dashboard/admin`, which returns:

| Area | Contents | Source module |
|---|---|---|
| Counts | Active and inactive users | Identity |
| Counts | Active and inactive products, active categories | Catalog |
| Counts | Orders and revenue in the last 30 days | Ordering |
| Charts | Users registered per day | Identity |
| Charts | Orders per day and revenue per day | Ordering |
| Charts | Top products by revenue | Ordering |
| Recent activity | Latest audit entries: who did what, in which module and on which screen | Auditing |

The service behind it lives in the API host and asks each module through its `Contracts`
interface, then stitches the answers together. Every day in a chart's window is present, so
a day with no orders is drawn as zero instead of the line jumping straight over it.

### Customer dashboard

**Your account > My Dashboard** (`/account/dashboard`, needs `dashboard.own`) calls
`GET /api/v1/dashboard/customer`:

- Total orders and total spent, plus orders and spend in the last 30 days.
- Number of orders still pending.
- Spend per day and orders per day charts.
- The most recent orders with their status, total and item count.

The endpoint takes no user id. The server reads the caller's id from the access token, so a
customer can only ever see their own numbers.

### Storefront and search

- The home page lists active products with paging, sorting and filters for category, price
  range and stock. Every filter is kept in the URL, so a filtered page can be bookmarked,
  shared and restored with the back button.
- **Search** suggests up to 10 products as the user types. Requests are debounced and a
  newer keystroke cancels the older request. It matches the start of product names, which lets
  SQL Server use the name index instead of scanning the table.
- **New arrivals** shows products added in the last 30 days.
- Anonymous visitors never see inactive products. Anonymous product and category responses
  are cached and the cache is cleared by any admin write.

### Cart

The cart works differently for guests and signed-in users:

| | Guest | Signed in |
|---|---|---|
| Stored in | The browser (`localStorage`) | The `ordering.Carts` table |
| Holds | Product ids and quantities only | Product ids and quantities |
| Expires | 1 hour after the last change, swept every 60 seconds | Does not expire |
| Prices | Fetched from the server on every render | Fetched from the server on every render |
| Needs | Nothing | `cart.own` |

- Prices are never stored in the browser or trusted from it. Changing a price in
  `localStorage` has no effect because the server prices every line from the catalog.
- **When a guest signs in**, the local cart is merged into their server cart. Quantities of
  the same product are added together, each line is clamped to the stock available, inactive
  or deleted products are dropped and reported back and the local cart is cleared once the
  merge succeeds. The merge request carries a token, so a retry within 5 minutes cannot add the
  items twice.
- A line whose quantity was reduced to match stock is flagged so the page can explain why.

### Checkout

1. **Re-price.** The server prices every line again from the catalog. If a product has been
   deleted, deactivated or has too little stock, the checkout is refused with `409` and a
   reason for each affected line. Nothing is silently removed and the customer never pays a
   total they did not see.
2. **Reserve stock.** Ordering asks Catalog to reserve all lines through
   `ICatalogModuleApi`. The reservation is all-or-nothing: either every line is reserved or
   none is.
3. **Create the order.** Product names, SKUs, unit prices and the shipping address are copied
   onto the order, so it stays correct if the product is renamed or repriced later. The order
   gets a unique number such as `ORD-20260823-000147` and starts as `Pending`.
4. **Payment.** The chosen method (cash on delivery, card or bank transfer) is recorded. No
   payment gateway is connected yet. The step still exists, so a declined payment would
   release the reserved stock.
5. **Finish.** The signed-in user's cart is marked as converted, an `OrderPlaced` event is
   published after the database commit and the confirmation page shows the order number.

**Guest checkout** (`POST /api/v1/checkout/guest`, no sign-in) sends the cart lines with the
order and saves the guest's name, email, phone and address as a guest profile keyed on email.
If that email already belongs to an account, the confirmation page suggests signing in, but
the order is **not** linked to the account: the guest's email was never verified, so linking
would let anyone attach orders to someone else's account. If the guest registers later, a
`UserRegistered` event links the guest profile to the new account.

Signed-in checkout needs `checkout.own`.

### Orders and cancellation

Every order moves through a fixed set of statuses. The rules live on the `Order` entity, so
the admin screen and the customer's cancel button obey the same table:

```
Pending -> Confirmed -> Processing -> Shipped -> Delivered -> Refunded
   |           |            |
   +-----------+------------+-------> Cancelled
```

| Who | Can do | Needs |
|---|---|---|
| Customer | View their own orders with date filters and open the detail page | `orders.read.own` |
| Customer | Cancel their own order while it is `Pending` or `Confirmed` | `orders.read.own` |
| Admin | View every order | `orders.read.all` |
| Admin | Move an order to any status the table allows, including cancelling up to `Processing` | `orders.manage` |

- Every change writes a status history row with who made it, when and why.
- Cancelling releases the reserved stock back to the catalog.
- A move the table does not allow, such as `Delivered` back to `Pending`, is refused.
- The customer endpoints never take a user id. The server filters by the signed-in user, so
  requesting another customer's order id returns "not found".

### Catalog administration

**Administration > Products** and **Categories** list every row, including inactive ones.
The **New**, **Edit** and **Delete** buttons appear only with `catalog.products.write` or
`catalog.categories.write`.

- **Products** have a name, slug, SKU, short and long description, price and optional
  compare-at price with a currency, stock, category, a featured flag and images. Deactivating
  a product hides it from the storefront. Deleting is a soft delete.
- **Images** can be uploaded (several at once) or added as external addresses and one image
  is marked as primary. Uploaded files are stored by the API in a `ProductImages` folder under
  generated file names and served back through the API.
- **Categories** form a tree (the seed data uses two levels). A category cannot be moved
  under itself or under one of its own descendants. Deleting a category that still holds
  products is refused with `409` unless another category is chosen to receive them.
- Stock can never go negative: a reservation larger than the stock is refused rather than
  reduced.

### Offers

**Administration > Offers** lists the discount offers with their code, name, discount,
validity window, how many times each was used and whether it can currently be redeemed. An
offer is a percentage or fixed amount with a start and end date, an optional minimum order
amount and an optional redemption limit. The discount maths lives on the `Offer` entity and a
fixed discount can never push a total below zero. An offer code entered at checkout is recorded on the order, but
discounts, tax and shipping are not applied to totals yet: they are all computed in one method,
`Order.ApplyTotals`, which is where applying them will go.

### Audit trail

**Administration > Audit Trails** (`/admin/audit-trails`, needs `audit.read`):

- Every insert, update and delete in any module is recorded automatically, with the changed
  columns and their old and new values. Sign-ins, failed sign-ins and sign-outs are recorded
  too.
- Each entry stores who did it, their roles, IP address, browser, the HTTP method and path, a
  correlation id and the **screen** the change came from, which the SPA sends in an
  `X-Client-Page` header.
- The screen filters by action and module and **View** opens the old and new values directly
  under the row. The API also filters by text, entity, user, screen and date range.
- Properties such as password hashes and token hashes are marked `[NoAudit]` and never written.
- Capture never slows a request down or breaks it: entries are queued in memory and written
  in batches by a background service.
- The trail is **append-only**. There is no endpoint to edit or delete an entry, not even
  for an admin.

## Why a modular monolith

Most applications start as one deployable and most should stay that way for a long time.
The problem is not the single deployable. The problem is that without enforced boundaries
every part of the code gradually learns about every other part: an order handler joins the
users table, a product service reads the audit table, one transaction spans three areas of
the business. At that point the system cannot be split, cannot be reasoned about in pieces
and every change risks breaking something far away.

A modular monolith keeps the operational simplicity of one process while designing the
code as if the modules were separate services:

- **Each module owns its data.** Its tables sit in its own schema and no other module can
  query them.
- **Each module has a public contract.** Other modules call an interface and receive DTOs.
  They never see entities, the `DbContext` or internal services.
- **Communication is explicit.** A synchronous question goes through a `Contracts`
  interface. A notification goes through an integration event.
- **The rules are checked by machines.** C# `internal` visibility makes most violations
  impossible to compile and the architecture test suite catches the rest.

The design goal is one question that every change is measured against: *could this module
be extracted into its own service by swapping its `Contracts` implementation for an HTTP
client, moving its schema to its own database and replacing in-process events with a
broker?* If extraction would require untangling a query or a transaction, a boundary has been
crossed.

## Modular monolith vs microservices

| Concern | Modular monolith (ShopHub) | Microservices |
|---|---|---|
| Deployment | One artifact, one pipeline | One pipeline per service, plus orchestration |
| Cross-module call | In-process method call, no serialization, no network failure | HTTP or gRPC call that can time out, retry or partially fail |
| Transactions | Local to a module, never shared across modules | Distributed; needs sagas or compensation |
| Data consistency | Immediate inside a module, events for the rest | Eventual almost everywhere |
| Debugging | One process, one stack trace, one log stream | Distributed tracing across services |
| Local development | `dotnet run` plus `npm run dev` | Many services, containers and a message broker |
| Refactoring a boundary | Compiler finds every call site | Versioned API changes coordinated across teams |
| Infrastructure cost | One host, one database | Many hosts, many databases, gateway, broker, service discovery |
| Independent scaling | The whole app scales together | Each service scales on its own |
| Independent deployment | Not possible | Each service ships on its own schedule |
| Technology per service | One stack | Free choice per service |

**What ShopHub gains by staying a monolith**

- No network hop between modules, so no retries, timeouts, circuit breakers or partial
  failures to design for.
- Checkout reserves stock in Catalog and writes the order in Ordering inside one request.
  In microservices that becomes a distributed operation with a third outcome - *unknown* -
  when a response is lost after the reservation committed.
- Integration tests run the real host against a real database in a single process.
- One deployment and one database to operate, back up and monitor.

**What it keeps from microservices**

- Clear ownership: each module owns its schema, its migrations and its public contract.
- Low coupling: a module can be rewritten internally without touching any other module.
- A tested extraction path: the `Contracts` interfaces are already the only way in, so
  replacing one with an HTTP client does not change a single call site.

**What extraction would actually cost here**

| Module | Cost | Why |
|---|---|---|
| Auditing | Low | Writes are already fire-and-forget onto a queue; only the drain changes |
| Catalog | Moderate | Reads are batched and id-based; stock reservation needs an idempotency key or a saga |
| Identity | Moderate, disruptive | Permission resolution runs on every authorized request and would become a network hop |
| Ordering | Highest | Checkout is the one business operation that genuinely spans two modules |

There are no cross-module joins to remove, because the type system made them impossible to
write. That is usually the largest cost of an extraction and here it is zero. The remaining
cost is essential to the business operations rather than accidental to the code, which is
exactly what the modular design is meant to leave behind. The sensible moment to extract a
module is when it develops a genuinely different scaling or availability profile from the
rest - and none currently does.

## Backend architecture

### The four modules

| Module | Schema | Owns | Public contract |
|---|---|---|---|
| **Identity** | `identity` | Users, roles, permissions, refresh-token families, role-driven menus | `IIdentityModuleApi` |
| **Catalog** | `catalog` | Products, categories, images, offers, storefront browse and search | `ICatalogModuleApi` |
| **Ordering** | `ordering` | Carts, checkout, orders, order status history, guest-checkout profiles | `IOrderingModuleApi` |
| **Auditing** | `audit` | The append-only audit trail written for every module | `IAuditWriter`, `IAuditModuleApi` |

Each module is two assemblies:

- `ShopHub.Modules.<Name>` - the implementation. Everything in it is `internal` except one
  registration type that implements `IModule`.
- `ShopHub.Modules.<Name>.Contracts` - the public surface. One interface and its DTOs, with
  no reference back to the implementation assembly.

Splitting a module into two projects is what makes the boundary checkable. "Does Ordering
reference Catalog's implementation?" has an exact answer in the assembly reference table, so
the question never depends on someone reading imports carefully.

### Anatomy of a module

Every module has the same shape, so moving between modules costs nothing. Catalog as the
example:

```
src/Modules/Catalog/
  ShopHub.Modules.Catalog.Contracts/
    ICatalogModuleApi.cs            the only thing other modules may use

  ShopHub.Modules.Catalog/
    CatalogModule.cs                the only public type: RegisterModule + MapEndpoints

    Domain/                         behaviour lives on the entities, not in handlers
      Product.cs                    stock rules: Reserve refuses rather than clamping
      Category.cs                   self-referencing tree, cycle-checked
      Offer.cs                      percentage or fixed discounts

    Features/                       one vertical slice per use case
      Products/
        ProductEndpoints.cs         internal static class, Map...Endpoints over a route group
        ProductService.cs           the use case logic
        ProductContracts.cs         request and response DTOs for this slice
        ProductValidators.cs        FluentValidation rules
        ProductImageStorage.cs      slice-specific infrastructure
      Categories/
      Offers/

    Persistence/
      CatalogDbContext.cs           internal, mapped to the catalog schema
      Configurations/               EF Core entity configurations
      Migrations/                   own history table: __EFMigrationsHistory_catalog
      CatalogSeeder.cs              deterministic Development seed data
      CatalogInitializer.cs         applies migrations and seeds on startup

    Infrastructure/
      CatalogModuleApi.cs           implements ICatalogModuleApi
      CatalogCacheInvalidator.cs    evicts cache entries by tag after writes

    EventHandlers/                  (Ordering) consumes other modules' integration events
```

**Why vertical slices.** A feature such as "browse products" touches an endpoint, a service,
DTOs and validation. Keeping them in one folder means a change to one use case is a change
to one folder, rather than a walk through `Controllers/`, `Services/`, `Models/` and
`Validators/` layers that each hold a fragment of every feature.

**Why behaviour sits in `Domain/`.** Rules such as "a reservation larger than the stock is
refused" or "a customer may only cancel before Processing" live on the entity (`Product`,
`Order`). They hold no matter which endpoint, service or future caller reaches them.

### Which files follow the pattern

| Role | Identity | Catalog | Ordering | Auditing |
|---|---|---|---|---|
| Module registration | `IdentityModule.cs` | `CatalogModule.cs` | `OrderingModule.cs` | `AuditingModule.cs` |
| Public contract | `IIdentityModuleApi.cs` | `ICatalogModuleApi.cs` | `IOrderingModuleApi.cs` | `IAuditWriter.cs` |
| Contract implementation | `Infrastructure/IdentityModuleApi.cs` | `Infrastructure/CatalogModuleApi.cs` | `Infrastructure/OrderingModuleApi.cs` | `Infrastructure/AuditTrailWriter.cs` |
| Internal `DbContext` | `IdentityDbContext` | `CatalogDbContext` | `OrderingDbContext` | `AuditingDbContext` |
| Feature slices | `Auth`, `Users`, `Roles`, `Access` | `Products`, `Categories`, `Offers` | `Carts`, `Checkout`, `Orders` | `AuditTrails` |
| Event handlers | - | - | `EventHandlers/UserRegisteredHandler.cs` | - |

Outside the modules:

| File | Role |
|---|---|
| `src/Api/ShopHub.Api/Program.cs` | Lists the four modules explicitly and composes them |
| `src/Shared/ShopHub.Shared.Infrastructure/Modules/IModule.cs` | The contract every module registration implements |
| `src/Shared/ShopHub.Shared.Infrastructure/Events/IEventBus.cs` | Publishing integration events |
| `src/Shared/ShopHub.Shared.Infrastructure/Events/InProcessEventBus.cs` | The in-process implementation |
| `src/Shared/ShopHub.Shared.Contracts/Events/` | Integration event types shared by producer and consumer |
| `src/Api/ShopHub.Api/Dashboards/DashboardService.cs` | Cross-module read composition |
| `tests/ShopHub.ArchitectureTests/ModuleCatalog.cs` | The list of modules the boundary tests check |

### How the host composes modules

`ShopHub.Api` is the only executable. It knows about modules through one interface:

```csharp
public interface IModule
{
    string Name { get; }
    IServiceCollection RegisterModule(IServiceCollection services, IConfiguration configuration);
    IEndpointRouteBuilder MapEndpoints(IEndpointRouteBuilder endpoints);
}
```

`Program.cs` lists the modules explicitly rather than scanning assemblies:

```csharp
IModule[] modules =
[
    new IdentityModule(),
    new CatalogModule(),
    new OrderingModule(),
    new AuditingModule(),
];
```

Each module registers its own `DbContext`, services, validators, `Contracts` implementation
and event handlers in `RegisterModule` and maps its own route group in `MapEndpoints`. The
host never reaches inside. An explicit list was chosen over assembly scanning because it is
readable, it fails at compile time when a module is renamed and adding a module is a one-line
change that shows up plainly in review.

### Talking across modules

There are exactly two mechanisms and the choice between them is deliberate.

| Need | Mechanism | Example |
|---|---|---|
| An answer now | Call the other module's `Contracts` interface | Ordering prices a cart through `ICatalogModuleApi` |
| Tell others something happened | Publish an integration event on `IEventBus` after the transaction commits | Identity publishes `UserRegisteredIntegrationEvent` |

**Synchronous calls.** `CheckoutService` and `CartPricer` in Ordering depend on
`ICatalogModuleApi` to re-price lines and reserve stock and on `IIdentityModuleApi` to check
whether a guest email belongs to a registered user. They never join to `catalog.Products` or
`identity.Users`. The calls return `Contracts` DTOs, never entities. Today each call is a
normal method call; after an extraction the implementation behind the interface would become
an HTTP client and no call site would change. The interfaces are designed for that future:
calls are batched and id-based, so a checkout of ten lines is one call rather than ten.

**Integration events.** When a user registers, `AuthService` in Identity publishes
`UserRegisteredIntegrationEvent`. Ordering's `UserRegisteredHandler` consumes it and links any
guest checkout profile with that email to the new account. Identity does not know Ordering
exists. The event types live in `ShopHub.Shared.Contracts`, so the consumer never references
the producer. Events are published only **after** the publisher's transaction commits, so no
module ever reacts to a change that was rolled back and each handler runs in its own DI
scope so it never joins the publisher's transaction.

**A known trade-off.** Delivery is in-process and a failing handler is logged and swallowed,
which is at-most-once delivery. The upgrade path is a transactional outbox behind the same
`IEventBus` interface, so publishers would not change. Nothing that needs guaranteed delivery
is built on the bus until that exists.

### Data ownership

- One SQL Server database, four schemas: `identity`, `catalog`, `ordering`, `audit`.
- Every entity maps to its own module's schema. An architecture test asserts it against the
  real EF Core model.
- **No foreign keys across schemas.** A reference to another module's row is a plain indexed
  `Guid` column validated in application code, so each schema can move to its own database
  without a constraint blocking it.
- **No cross-schema JOINs.** What a module needs from another module at write time is
  snapshotted. An order line stores the product name and unit price it was sold at, so the
  order history stays correct when the product is renamed or repriced later.
- Each module has its own migrations and its own history table
  (`__EFMigrationsHistory_identity` and so on), so one module's pending migration never blocks
  another's deploy.

### Cross-module reads

The admin dashboard needs numbers from all four modules. It is composed in
`src/Api/ShopHub.Api/Dashboards/DashboardService.cs` from four `Contracts` calls
(`IIdentityModuleApi`, `ICatalogModuleApi`, `IOrderingModuleApi`, `IAuditModuleApi`), never
from a SQL query across schemas.

That is why `Dashboards/` lives in the host and not in a module: it belongs to no single
module and it cannot open any module's `DbContext` because every `DbContext` is `internal`.
It costs a few extra round trips to the database and buys the property that makes the whole
design worthwhile - any module can be lifted out without rewriting its consumers.

### The shared projects

| Project | May reference | Contains |
|---|---|---|
| `ShopHub.Shared.Kernel` | Nothing but the BCL | `Result`, `Entity`, `PagedRequest` / `PagedResult`, `IClock`, `ICurrentUser`, domain exceptions |
| `ShopHub.Shared.Contracts` | Kernel | Integration event types |
| `ShopHub.Shared.Infrastructure` | Kernel, Contracts | `IModule`, `IEventBus`, error handling, auth, rate limiting, caching, correlation, audit capture |

None of them may reference a module. Audit **capture** (the `SaveChanges` interceptor) lives
in `Shared.Infrastructure` because it runs inside every module's `DbContext`, while audit
**storage** lives in the Auditing module. If capture lived in Auditing, every other module
would have to reference Auditing's implementation, which the boundary rules forbid.

### How the boundaries are enforced

Enforcement happens at two levels.

**The compiler.** Each implementation assembly exposes exactly one public type - its
`IModule`. The `DbContext`, entities, endpoints, services and handlers are all `internal`, so
reaching into another module does not compile. When a type is added, `internal` is the
default and `public` is a decision that has to be justified.

**The architecture tests.** `tests/ShopHub.ArchitectureTests` uses NetArchTest and EF Core
model inspection:

| Test | What it prevents |
|---|---|
| `Module_DoesNotDependOn_AnotherModulesImplementation` | Ordering referencing Catalog's implementation assembly |
| `Module_ReachesOtherModules_OnlyThroughContracts` | Any cross-module path other than a `Contracts` project |
| `ControllersAndRepositories_DoNotReach_AcrossModules` | A naming convention being used as an excuse to cross a boundary |
| `EveryEntity_MapsToItsOwnModuleSchema` | An entity leaking into another module's schema |
| `ModuleDbContexts_AreDiscoverable` | The schema test passing vacuously because it found nothing to check |
| `DbContexts_AreNotPublic` | Another module opening this module's `DbContext` |
| `Endpoints_AreInternal` | Endpoint types becoming an accidental public API |
| `OnlyTheModuleRegistrationType_IsPublic` | The public surface of a module growing by accident |
| `Api_SeesOnlyPublicModuleRegistrationSurface` | The host depending on module internals |
| `SharedKernel_DependsOnNoShopHubAssembly` | The kernel picking up a dependency on anything above it |
| `SharedContracts_DependsOnNoModuleAssembly` | Event contracts coupling to a producer |
| `SharedInfrastructure_DependsOnNoModuleAssembly` | Cross-cutting code coupling to a module |

The rules run against every module listed in `ModuleCatalog.cs` (52 test cases in total).
They assert on **assembly references** rather than namespace strings, so a violation hidden
inside a method body cannot slip past. The suite was verified by deliberately adding a
Catalog to Ordering project reference and watching it fail.

### Request lifecycle

```
HTTP request
  -> UseExceptionHandler      RFC 9457 ProblemDetails with a stable "code"
  -> UseCorrelationId         X-Correlation-Id in and out, pushed into the log context
  -> Serilog request logging  one line per request: user, page, status, elapsed
  -> ResponseCompression      Brotli / Gzip
  -> CORS                     explicit origins with AllowCredentials
  -> RateLimiter              auth | anonymous | authenticated | write | checkout
  -> OutputCache              anonymous storefront GETs only
  -> module endpoint          internal, permission-checked
       -> service -> own DbContext (own schema only)
       -> needs another module now?     that module's Contracts interface
       -> something happened?           IEventBus, after the commit
```

### Backend conventions

- **Permission-based authorization.** Every route declares `.RequireAuthorization(permission)`
  or `.AllowAnonymous()`. Roles are data, so adding a role is a database change rather than a
  deploy. Menus are granted per role in the same way.
- **Every list endpoint is paged**, including admin screens and dropdowns. `PageSize` clamps
  to `[1, 100]`.
- **Reads project, they do not materialize**: `AsNoTracking()` plus `.Select(...)` into a DTO.
- **Sorting is whitelisted per endpoint** and every sort has a tiebreaker, so paging never
  skips or duplicates rows.
- **Errors are ProblemDetails** with a machine-readable `code`. Clients branch on the code,
  never on the message. Outside Development, 5xx bodies are sanitized.
- **Caching** uses `HybridCache` for DTOs (never entities, never per-user data) and output
  caching for anonymous storefront responses. Writes invalidate both by tag.
- **UTC everywhere**, with column names ending in `Utc`. Money is `decimal(18,2)` with an
  explicit `CurrencyCode`.
- **Central Package Management** in `Backend/Directory.Packages.props`. The build runs with
  warnings as errors and code style enforced.

## Frontend architecture

The SPA mirrors the backend's modular design. Where the backend has modules with a
`Contracts` project, the frontend has feature folders with an `index.ts` public surface.

### Feature folders

```
Frontend/src/
  app/                     the shell: router, layouts, route guards, providers
  features/
    auth/                  sign-in, registration, session loading
    catalog/               storefront grid, product detail, search, filter panel
    cart/                  local cart, server cart, merge on sign-in
    checkout/              checkout and order confirmation
    orders/                purchase history and order management
    account/               customer dashboard and profile
    admin/                 admin dashboard, catalog CRUD, users, roles, audit, access
  shared/
    api/                   httpClient.ts, authStore.ts, shared API types
    components/ui/         Button, Field, Modal, DataTable, Pagination, Charts, Toast, States
    hooks/                 useListParams, useDebounce, useTheme
    lib/                   formatting, permissions, class name helpers
  styles/index.css         Tailwind v4 design tokens, CSS-first
  test/                    test setup, accessibility and import-boundary tests
```

Each feature keeps its own `api/`, `components/` and `pages/` folders.

### The feature boundary

- A feature may import from `shared/` and from its own folder.
- A feature may reach another feature **only through that feature's `index.ts`**. For
  example `features/cart/index.ts` exports the cart store and the cart API functions, while
  `localCart.ts` internals stay private and free to change.
- `src/app/` is the composition root. It is the only place that wires feature pages into the
  router, the same way `Program.cs` wires modules into the host.

This is enforced twice:

1. `no-restricted-imports` in `Frontend/.oxlintrc.json` rejects the common deep-import shapes
   such as `@/features/*/api`.
2. `src/test/boundaries.test.ts` resolves every relative import in every feature to an
   absolute path and fails if it lands inside another feature below its `index.ts`. Resolving
   the path means an extra `../` cannot sidestep the rule.

### State and data flow

| Concern | Where it lives | Why |
|---|---|---|
| Server state | React Query | Caching, retries and background refetching without hand-written effects |
| Auth session | zustand store in `shared/api/authStore.ts` | The access token is held **in memory only**, never in `localStorage` |
| Refresh token | `HttpOnly` cookie set by the API | JavaScript cannot read it at all, so an XSS flaw cannot steal it |
| Guest cart | zustand plus `localStorage` | Survives a reload; stores ids and quantities, never prices |
| List filters | URL query string (`useListParams`) | Shareable, refresh-safe and back-button friendly |
| Sidebar menu | Returned by `/api/v1/auth/me` | Menu access is data; revoking a menu needs no deploy |

### The HTTP client

All HTTP goes through `shared/api/httpClient.ts`. Features never call `fetch` directly. The
client:

- attaches the bearer token, a correlation id and the current page for the audit trail
- refreshes the access token shortly before it expires and again on a `401`, with a single
  in-flight refresh shared by every concurrent request, so a burst of requests never rotates
  the refresh token twice
- decodes ProblemDetails into a typed `ApiError` so the UI branches on `code`
- tells "the API did not answer" apart from "the API failed", so a backend that is still
  starting shows a waiting state instead of an error

### Access control in the UI

Route guards in `app/guards.tsx` and permission checks in `shared/lib/permissions.ts` hide
screens and buttons the user cannot use. This is presentation only: every endpoint checks the
same permission on the server, which is what actually refuses a request.

### Quality gates

- TypeScript strict mode across the app, node and test projects (`npm run typecheck`).
- oxlint, with `console.log` treated as an error (`npm run lint`).
- Vitest and Testing Library for components, the HTTP client, the retry policy and the
  feature boundary.
- axe-core runs inside the test suite (`src/test/a11y.test.tsx`), so accessibility is asserted
  rather than assumed.

### 2. Database

The Development connection string is in `Backend/src/Api/ShopHub.Api/appsettings.Development.json`

```bash
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -Q "IF DB_ID('ShopHub') IS NULL CREATE DATABASE ShopHub;"
```

In Development the host applies every module's migrations and seeds on startup. Running
`dotnet ef` by hand is only needed to inspect or stage a migration and always needs
`--context`, because the solution has four `DbContext` types:

```bash
cd Backend
dotnet ef database update --context IdentityDbContext --project src/Modules/Identity/ShopHub.Modules.Identity --startup-project src/Api/ShopHub.Api

dotnet ef database update --context AuditingDbContext --project src/Modules/Auditing/ShopHub.Modules.Auditing --startup-project src/Api/ShopHub.Api
```

```bash
cd Backend
dotnet run --project src/Api/ShopHub.Api
```

## Adding a fifth module

Adding a module such as `Shipping` follows the same shape as the existing four:

1. Create `ShopHub.Modules.Shipping` and `ShopHub.Modules.Shipping.Contracts`. The
   implementation references its own Contracts project and the shared projects, never another
   module's implementation.
2. Add `ShippingModule : IModule` as the only public type. Register the module's services in
   `RegisterModule` and its route group in `MapEndpoints`.
3. Give it an `internal` `ShippingDbContext` mapped to a `shipping` schema, with its own
   migrations history table `__EFMigrationsHistory_shipping`.
4. Expose what other modules need through `IShippingModuleApi` in the Contracts project, and
   consume other modules only through theirs or through integration events.
5. Add `new ShippingModule()` to the module list in `Program.cs`.
6. Register it in `tests/ShopHub.ArchitectureTests/ModuleCatalog.cs` so every boundary rule
   applies to it from the first build.
